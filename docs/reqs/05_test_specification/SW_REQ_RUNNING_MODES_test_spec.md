# Test Specification: SW_REQ_RUNNING_MODES

**Source:** `docs/reqs/03_functional_requirements/functional_requirements.rst`

## Requirement Summary

This test specification covers the child requirements under the parent `SW_REQ_RUNNING_MODES`:
`SW_REQ_RUNNING_MODES_ONETIME`, `SW_REQ_RUNNING_MODES_PERIODIC`, and
`SW_REQ_RUNNING_MODES_BUILT_IN`. The PERIODIC timer-event relationship is specified by
`SW_REQ_EVENT_DRIVEN_TIMER_SOURCE`.

**Fit Criterion:** Each child behavior is tested independently: ONETIME executes once and exits,
PERIODIC repeats at its interval, and both modes operate without an external scheduler.

## Test Design Techniques

- Equivalence Partitioning: mode classes {ONETIME, PERIODIC, invalid mode}.
- Boundary Value Analysis: PERIODIC interval at minimum supported value and typical value.

## Test Cases

### TC_MODE_01 — ONETIME mode executes once and exits
*Type: Positive · Priority: High*

Title: ONETIME mode executes once and exits.
Satisfies:
   - SW_REQ_RUNNING_MODES
   - SW_REQ_RUNNING_MODES_ONETIME
Objective: Happy — Verify ONETIME performs one complete cycle and terminates.
Steps:
   - 1. Start an in-process TCP echo peer on `127.0.0.1:<ephemeral-port>` and configure a Connix CLIENT with mode `ONETIME`, payload `PING`, and a `2s` process timeout.
   - 2. Start Connix and capture cycle-start, send, receive, close events, peer receive count, and process exit.
   - 3. After exit, inspect the peer count and event vector for additional cycles.

Expectations:
   - 1. The peer becomes ready and the CLIENT configuration is accepted.
   - 2. Exactly one cycle sends `PING`, receives the echo, closes, and exits within `2s`.
   - 3. The peer observes exactly one connection and no event occurs after the process exits.

TestData:
   - Mode `ONETIME`; protocol `TCP`; host `127.0.0.1`; ephemeral port; payload `PING`.
   - Capture ordered events, peer receive count, exit status, and elapsed time; close peer and release port.

### TC_MODE_02 — PERIODIC mode repeats on configured interval
*Type: Positive · Priority: High*

Title: PERIODIC mode repeats on configured interval.
Satisfies:
   - SW_REQ_RUNNING_MODES
   - SW_REQ_RUNNING_MODES_PERIODIC
Objective: Happy — Verify PERIODIC triggers repeat at the configured interval.
Steps:
   - 1. Start an in-process TCP echo peer on `127.0.0.1:<ephemeral-port>` and configure a Connix CLIENT with mode `PERIODIC`, interval `2s`, and payload `PING`.
   - 2. Start Connix and collect cycle-start timestamps, peer connection count, and process output for `10s`.
   - 3. Stop the test after the fifth trigger and compare adjacent trigger timestamps.

Expectations:
   - 1. The peer and PERIODIC CLIENT start successfully without an external scheduler.
   - 2. Five cycles start during the `10s` observation window, each sends `PING`, receives the echo, and closes before the next cycle.
   - 3. Adjacent cycle-start timestamps are approximately `2s` apart within the documented scheduler tolerance, with no duplicate or overlapping cycle.

TestData:
   - Mode `PERIODIC`; interval `2s`; observation window `10s`; protocol `TCP`; payload `PING`.
   - Peer `127.0.0.1:<ephemeral-port>`; timestamp and connection-count collectors; teardown stops Connix and releases port.

### TC_MODE_03 — PERIODIC mode requires no external scheduler
*Type: Positive · Priority: Medium*

Title: PERIODIC mode requires no external scheduler.
Satisfies:
   - SW_REQ_RUNNING_MODES
   - SW_REQ_RUNNING_MODES_PERIODIC
   - SW_REQ_RUNNING_MODES_BUILT_IN
Objective: Happy — Verify PERIODIC triggers are generated by the Connix process itself.
Steps:
   - 1. Start Connix CLIENT with mode `PERIODIC`, interval `1s`, and a local in-process echo peer; disable/remove any test-owned cron or systemd timer and record the host scheduler state.
   - 2. Let Connix run for `4s` while collecting cycle-start timestamps, process ID, child-process list, and peer connection count.
   - 3. Stop Connix and inspect the recorded process/scheduler data.

Expectations:
   - 1. Connix starts with no external scheduler entry for the test configuration.
   - 2. Four periodic cycles are generated by the running Connix process; no cron/systemd invocation or scheduler child process appears.
   - 3. Removing/stopping Connix stops further cycles, proving the repetition is owned by the process.

TestData:
   - Mode `PERIODIC`; interval `1s`; duration `4s`; local TCP peer `127.0.0.1:<ephemeral-port>`.
   - Capture process tree, scheduler-entry snapshot, cycle timestamps, and peer count; restore scheduler state and close peer.

### TC_MODE_04 — PERIODIC interval boundary: minimum supported interval
*Type: Boundary · Priority: Medium*

Title: PERIODIC interval boundary: minimum supported interval.
Satisfies:
   - SW_REQ_RUNNING_MODES
   - SW_REQ_RUNNING_MODES_PERIODIC
Objective: Edge — Verify stable PERIODIC operation at the documented minimum interval.
Steps:
   - 1. Obtain the documented minimum supported interval `MIN_INTERVAL` from the configuration schema, start an in-process TCP echo peer on `127.0.0.1:<ephemeral-port>`, and configure a CLIENT with mode `PERIODIC`, interval `MIN_INTERVAL`, and payload `PING`.
   - 2. Run Connix for exactly five trigger intervals while collecting cycle timestamps, completed-cycle count, error output, CPU/RSS samples, and peer connection count.
   - 3. Stop Connix and compare the captured values with the configured boundary and resource limits.

Expectations:
   - 1. `MIN_INTERVAL` is a documented positive value and the CLIENT/peer fixtures start successfully.
   - 2. Five cycles complete without a malformed-timer or scheduling error; each cycle sends `PING`, receives the echo, and closes before the next cycle.
   - 3. Trigger spacing is within the documented scheduler tolerance, no cycle overlaps, and the process remains stable without resource exhaustion during the five-interval run.

TestData:
   - `MIN_INTERVAL` from the refined configuration schema; mode `PERIODIC`; five intervals.
   - Protocol `TCP`; peer `127.0.0.1:<ephemeral-port>`; payload `PING`.
   - Capture cycle timestamps/count, peer count, stderr, CPU/RSS samples, and exit status; stop process and release port.

### TC_MODE_05 — Invalid/missing execution mode rejected
*Type: Error · Priority: High*

Title: Invalid/missing execution mode rejected.
Satisfies:
   - SW_REQ_RUNNING_MODES
   - SW_REQ_RUNNING_MODES_ONETIME
   - SW_REQ_RUNNING_MODES_PERIODIC
Objective: Error — Verify invalid and missing execution modes fail validation before scheduling or network activity.
Steps:
   - 1. Create two otherwise valid CLIENT configurations targeting `127.0.0.1:1`: one with `mode: CONTINUOUS` and one with the `mode` field omitted.
   - 2. Load each configuration separately while a transport-factory mock and scheduler mock record calls; capture validation output and exit status.

Expectations:
   - 1. Both configuration files are syntactically valid and differ only in the invalid/missing mode condition.
   - 2. Each load reports the missing/unsupported mode, exits non-zero, invokes neither the scheduler nor transport factory, and performs no network action.

TestData:
   - Config A: `{ "role": "CLIENT", "protocol": "TCP", "host": "127.0.0.1", "port": 1, "mode": "CONTINUOUS" }`.
   - Config B: same fields with `mode` omitted.
   - Capture validation output, exit status, scheduler/transport mock calls; no peer fixture.

### TC_MODE_06 — PERIODIC mode with invalid (e.g. zero or negative) interval rejected
*Type: Error · Priority: Medium*

Title: PERIODIC mode with invalid (e.g. zero or negative) interval rejected.
Satisfies:
   - SW_REQ_RUNNING_MODES
   - SW_REQ_RUNNING_MODES_PERIODIC
Objective: Error — Verify invalid PERIODIC intervals fail before timer creation.
Steps:
   - 1. Create two otherwise valid CLIENT configurations with mode `PERIODIC`, protocol `TCP`, host `127.0.0.1`, port `1`, and intervals `0s` and `-1s`.
   - 2. Load each configuration separately while a scheduler mock records timer creation; capture validation output and exit status.

Expectations:
   - 1. Both configurations are parsed successfully and differ only in the invalid interval value.
   - 2. Each load reports an invalid interval, exits non-zero, creates no periodic timer, and performs no network operation.

TestData:
   - Config A interval `0s`; Config B interval `-1s`; mode `PERIODIC`.
   - Capture validation output, exit status, scheduler calls, and transport-factory calls; no peer fixture.
